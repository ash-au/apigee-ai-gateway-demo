# Engineering Honesty, Accounting Rules & Architectural Trade-Offs

This document records the exact accounting rules, algorithmic adaptations from the research papers, and production trade-offs across all **5 Tabs** of this build so that any Staff Engineer, Principal Architect, or FinOps lead inspecting the system gets a transparent, verifiable answer.

---

## 1. Zero-Fudge Token & Cost Accounting Rules

1. **All LLM Token Counts Originate from Live Vertex AI `usageMetadata`:**
   * Every southbound LLM call returns `promptTokenCount`, `candidatesTokenCount`, and `thoughtsTokenCount` directly from Vertex AI (`australia-southeast1-aiplatform.googleapis.com` for `gemini-2.5-flash` and `aiplatform.googleapis.com` for `gemini-2.5-pro`).
2. **Internal Thinking Tokens (`thoughtsTokenCount`) Are Explicitly Surfaced and Billed:**
   * In Gemini 2.5 models, reasoning ("thinking") tokens are billed at the **output token rate** (`$10.00 / 1M` on Gemini 2.5 Pro; `$2.50 / 1M` on Gemini 2.5 Flash) and share the `maxOutputTokens` budget with `candidatesTokenCount`.
   * Both the Direct Baseline column and the Apigee X Gateway column explicitly display `thoughtsTokenCount` and bill them at the model's output rate.
3. **All Gateway Overhead (Embeddings, Summarizers, System 1 Jev Calls, & Cascade Escalations) Is Included in Billed Totals:**
   * **Semantic Cache Lookups (`text-embedding-005`):** Every cache lookup (whether a HIT or a MISS) bills the real `statistics.token_count` returned by Vertex AI `text-embedding-005` at `$0.025 / 1M` tokens (`embedding_overhead_tokens`).
   * **Context Pruning Summarization (`gemini-2.5-flash`):** When `X-Opt-Prune: true` condenses older conversation turns into a rolling state summary, the input, output, and thinking tokens consumed by that summarization call are added to `pruning_summarizer_overhead_tokens` and `pruning_summarizer_cost_usd`.
   * **TypeSafe Jev System 1 Inference (`jev-latest` on Tab 5):** Every call to `POST https://api.typesafe.ai/v1/systemone` returns `usage.input_tokens` and `usage.output_tokens`. Both Stage 1 (`SC-JevPreRoute`) and Stage 2 (`SC-JevPostVerify`) Jev input tokens are billed at TypeSafe's published rate of **`$0.042 / 1M` input tokens (`$42 / Btok`)** and **`$0.00` output tokens**, and are added into `total_jev_system1_cost_usd` and `total_cost_usd`.
   * **FrugalGPT & Jev SDE Cascade Escalations ($L_1 + L_2$ Double-Billing):** Whenever an $L_1$ (`gemini-2.5-flash`) response is rejected—either by Tab 1's reliability scorer ($g(q, a) < 0.80$) or by Tab 5's 5-head Jev `Noul` battery (`any_flag > fire_threshold`)—and escalated to $L_2$ (`gemini-2.5-pro`), the gateway sums **both** the $L_1$ attempt and the $L_2$ completion (plus all Jev Stage 1 + Stage 2 tokens) into the gateway's total cost. We never hide the cost of a rejected $L_1$ draft.

## 3. Production Trade-Offs & Candid Disclosure for Technical Buyers

1. **Deterministic Defect Injection Toggle (`simulate_l1_defect`) in Tab 5 Scenario 3:**
   * Modern `gemini-2.5-flash` is strong enough that on short 4-bullet RAG passages, it frequently answers accurately on the first try. If a presenter is demonstrating Stage 2 `Noul` Battery escalation live on stage, relying on a non-deterministic LLM hallucination is risky.
   * Therefore, Tab 5 exposes an explicit, visible checkbox (**"3. Inject Subtle L1 Defect (`simulate_l1_defect: bool`)"**, enabled by default on Scenario 3 and disabled on Scenarios 1, 2, and 4). When checked, `gateway-optimizer` substitutes a realistic defective $L_1$ draft (containing a fabricated region and an omitted constraint) before calling TypeSafe Jev's `/v1/systemone` endpoint so the audience can see Jev's live `Noul` battery probabilities spike (`0.89–0.99 <== FIRES`) and trigger a real $L_2$ `gemini-2.5-pro` recovery call. Unchecking the box audits the raw, unmodified `gemini-2.5-flash` output (as shown in Scenario 4).
2. **External SaaS Call (`api.typesafe.ai`) vs. In-Region VPC Hosting for System 1:**
   * Calling TypeSafe Jev (`https://api.typesafe.ai/v1/systemone`) from `australia-southeast1` takes `~185–225ms` per stage (including cross-region network RTT) and requires sending prompt/response state to TypeSafe's API using an API key stored in Google Cloud Secret Manager (`typesafe-api-key`).
   * *Production trade-off:* If strict data-residency rules require 100% of traffic to remain inside `australia-southeast1` VPC boundaries, teams can either deploy self-hosted encoder models (**DeBERTa-v3-NLI**, **Vectara HHEM-2.1**, or **RouteLLM**) on Cloud Run / Vertex AI Model Garden in Sydney (`~15–35ms` latency, at the cost of fixed task heads rather than Jev's arbitrary multi-question `Noul` battery) or request private/VPC deployment options from TypeSafe.
3. **CPU vs. GPU Latency on Tab 1 LLMLingua-2 Compression:**
   * On a 2-vCPU Cloud Run instance, `llmlingua-2-bert-base` takes `~1.5s–5.5s` on long multi-document RAG prompts (`350–1,000` tokens).
   * *Production recommendation:* Deploy `gateway-optimizer` on a Cloud Run **NVIDIA L4 GPU** instance in `australia-southeast1`, reducing `llmlingua-2` token classification latency from `~5s` on CPU to **`<45ms`**.
4. **Vertex AI Vector Search Dedicated Node Cost (`SHARD_SIZE_MEDIUM`) vs. In-Memory/Redis Cache:**
   * Apigee's native `<SemanticCacheLookup>` policy requires a Vertex AI Vector Search Index Endpoint (`e2-standard-16` for `SHARD_SIZE_MEDIUM`), which bills `~$1.08/hr` while deployed even at zero traffic.
   * That is why we built the **Suspend / Wake Node (`$0/hr`)** control in Tab 4 and `./infra/toggle_vector_search.sh off|on`, allowing teams to undeploy the index from the endpoint when not actively testing native XML caching while keeping the Index resource intact.
